An I/O core, TCP/UDP transports, and pluggable protocol stacks

One event loop. Every transport under it.

Keel is a portable, event-driven transport substrate for C: a composable event context (KlEventCtx) driving byte-stream (KlStream), listener (KlListener), and datagram (KlDatagram) transports, with built-in protocol families layered on top. Readiness and completion are orthogonal execution models behind one API. HTTP is the flagship family, not the definition.

#include <keel/keel.h>

static void handle_run(KlHttpRequest *req,
                       KlHttpResponse *res,
                       void *ctx) {
    (void)req;
    (void)ctx;

    static const char body[] =
        "{\"ok\":true,\"runtime\":\"keel\"}";
    kl_http_response_json(res, 200, body,
        sizeof(body) - 1);
}

int main(void) {
    KlHttpServer s;
    KlHttpServerConfig cfg = { .port = 7070 };

    if (kl_http_server_init(&s, &cfg) != 0)
        return 1;
    if (kl_http_server_route(&s, "GET", "/run",
            handle_run, NULL, NULL) != 0) {
        kl_http_server_free(&s);
        return 1;
    }
    int rc = kl_http_server_run(&s);
    kl_http_server_free(&s);
    return rc != 0;
}

The HTTP server is one protocol stack riding the runtime. The same event loop, socket seam, and transports carry the datagram transport, the WebSocket and SSE stacks, and Keel's own from-scratch async DNS resolver. Swap the event backend without changing a line of protocol code.

Keel v3.3.0

Process I/O on the same loop. Hardened across the stack.

Anonymous pipe pairs extend the stream transport to an embedder's child processes. Six rounds of C audits and their re-reviews tighten parsing, callback lifetime, TLS, DNS, HTTP/2, and completion I/O. Read the release and upgrade notes.

Anonymous pipe pairs

kl_anon_pipe_create returns a directional KlPipeStream and a native child end for your process spawner. POSIX engines use ordinary pipes through watchers; Windows uses private named pipes on IOCP. Keel leaves process creation to the embedder. Both ends start close-on-exec or non-inheritable.

Pipe API and platform limits, native-end handoff.

Writable-again callbacks

After KL_STREAM_WOULD_BLOCK, kl_stream_on_writable signals when to retry, on sockets and pipes alike. The retry reports whether capacity returned or the write side failed. Graceful close also completes after a terminal write failure.

Stream and close contract.

Limits and lifetime safety

Bounded chunk extensions and trailers, deferred async-client startup errors, TLS-aware pool APIs, and an optional redirect policy callback. DNS spoofing resistance, HTTP/2 limits and h2c upgrade handling, and ordered, bounded completion output receive fixes across the stack.

Upgrading from 3.2.0: rebuild all consumers against the new headers; Keel preserves source compatibility, not ABI compatibility. Build requirements are unchanged. Review the observable behavior changes: HTTP/2 client bodies default to a 16 MiB per-stream cap; mbedTLS client creation without a CA bundle now fails (unverified clients use an explicit insecure factory); and enum switches must account for KL_ERR_REDIRECT_REFUSED and KL_IO_RESOURCE_EXHAUSTED.

Build & test

One library. Two I/O models.

Keel builds as a static C library. Pick a readiness engine (epoll, kqueue, WSAPoll, poll) or a completion engine (io_uring, IOCP) at build time; the protocol stacks above never change.

shell local build 
# Get the v3.3.0 source release.
$ git clone --branch v3.3.0 --depth 1 https://github.com/artalis-io/keel.git
$ cd keel

# Build libkeel.a with the platform default (epoll / kqueue).
$ make

# Linux 5.6+: completion-native I/O over io_uring (SQE/CQE, splice).
$ make BACKEND=iouring

# Universal POSIX fallback; also enables Cosmopolitan APE builds.
$ make BACKEND=poll

# Native MSVC on Windows: same tree, same PAL, only the compiler mapping changes.
$ source scripts/msvc-env.sh
$ make CC=cl

# Run the test suite and example programs.
$ make test
$ make examples

Coverage is not a single number. Each execution model is exercised by a specific, reproducible gate, and they are not equivalent: a hosted CI unit suite, a sanitizer smoke, an integration harness, a strict compile gate, and a local-only firmware emulation each prove something different.

Architecture

Three layers, cleanly separated.

Keel is not an HTTP library with an event loop bolted on. It is an I/O runtime with protocols on top, and the axes stay orthogonal: the event model and the socket implementation are independent, and every protocol sits above both without knowing which is in use.

The tell is DNS: Keel ships its own async resolver, built from scratch on the UDP layer. A runtime that already hosts a non-HTTP protocol is a runtime, not a web server.

Living architecture docs: overview, invariants, public API.

Protocol stacks pluggable, above both axes
HTTP/1.1, HTTP/2, WebSocket (RFC 6455), Server-Sent Events, and a built-in async DNS resolver: dual A+AAAA, EDNS0, DNS cookies, TCP fallback, /etc/hosts. Sync and async HTTP clients, connection pooling, redirects, compression, and PROXY-protocol recovery ride the same core.
Transports peers on one loop
Byte streams (KlStream), listeners (KlListener), and datagrams (KlDatagram) are peers on the same loop, not an afterthought. Named pipes and anonymous process-I/O pipes expose the same stream contract, including writable-again backpressure callbacks. KlDatagram exposes async receive with source and destination addressing; batching (recvmmsg/sendmmsg), GSO/GRO offload, multicast join/leave, and per-packet ECN/DSCP are capability-gated extensions, available where the platform and provider support them.
I/O runtime readiness + completion core
A composable event context (KlEventCtx) over an orthogonal event core: readiness (epoll/kqueue/WSAPoll/poll) and completion (io_uring/IOCP), on a platform-neutral socket seam (POSIX/Winsock). Single-threaded per worker, with timers, async connection suspension, thread-pool offload, backpressure, and zero-copy splice file sends. Scale horizontally with SO_REUSEPORT.
Principles

Small pieces. Explicit edges.

Orthogonal axes

The event model and the socket implementation are independent axes; allocator, parser, body reader, TLS, resolver, and compression are replaceable vtables. An audit confirmed protocol code contains no platform event or socket logic.

No forced buffering

Buffer, file, and streaming response modes let services avoid copying when sendfile, writev, chunking, or backpressure are the right tool.

Batteries optional

No mandatory OpenSSL, no forced runtime. Bring your own allocator, TLS, parser, and compression backend, or use the defaults. One vendored parser (llhttp), 2-second clean builds.

Unified

One seam under every layer.

A C service is often assembled from a separate event loop, HTTP server, and DNS resolver, each with its own build system and dependency tree. Keel puts the I/O core, the transports, the protocol families, and its own resolver behind a single socket-and-event seam. Swap the event model or the socket provider once, below everything.

One I/O core

Readiness and completion behind one API, over a POSIX/Winsock socket seam. A new event backend or socket provider is a drop-in below every transport and protocol at once, verified by the axis audit.

Streams and datagrams

KlStream, KlListener, and KlDatagram are peers on the same loop. Socket streams, named pipes, and anonymous pipe pairs share the stream contract; TCP and UDP protocols use the same runtime.

Protocols on top

HTTP/1.1, WebSocket, SSE, and a from-scratch async DNS resolver ship in-tree; HTTP/2 and TLS are pluggable vtables. None of them include a platform networking header or touch an event engine directly.

This is a description of Keel's own composition, not a scoreboard against other projects. The load-bearing claim is architectural: the axes stay orthogonal, so an alternate event engine or socket stack drops in below every layer at once. See docs/architecture/invariants.md.

Performance

Bounded paths you can measure.

Each connection runs a bounded path: accept → read → write, with zero-copy pointers into read buffers, splice/sendfile on the file path, and recvmmsg/sendmmsg batching on the datagram path where the platform supports it. The benchmark endpoints below measure what routing, middleware, and body reading add over a bare baseline; run make bench to measure the delta on your own hardware.

epoll is the default on Linux; io_uring is the completion-native path one build flag away (make BACKEND=iouring), and runs the same protocol code. Which is faster depends on workload and kernel, so the honest answer is to measure both.

feature cost

What's next

The architecture predicts the roadmap.

Because protocols ride the runtime and the axes stay orthogonal, the next steps are additive: a new stack on the existing core, or a new provider below every stack, never a rewrite. The QUIC and MQTT items below are directions, not shipped features; the alternate-stack card separates what already runs from what would slot in next.

QUIC / HTTP-3
planned

Not yet shipped. A protocol family over UDP + TLS. The async UDP datagram layer, the completion backends, and the TLS vtable already exist, so HTTP/3 would be "another stack," as HTTP/2 was. Prerequisite: UDP pktinfo/GSO/GRO parity on the completion path.

MQTT
planned

Not yet shipped. A TCP pub/sub protocol that would drop onto the existing connection core as a peer to the HTTP stack, with no runtime changes needed.

Alternate net stacks
shipped + planned

Shipped: the stack (server, client, UDP, DNS, HTTPS) runs on a stock libkeel.a over a bare lwIP TCP/IP stack (NO_SYS raw callbacks), and a stock async client runs inside UEFI firmware over EFI_TCP4/UDP4 tokens (plaintext, HTTPS with CA / hostname / validity-time checks, and DNS), exercised on QEMU/OVMF. Planned: AF_XDP or DPDK would slot in the same way, below every protocol stack.

How it works

Event loop first. Protocols around it.

A composable event context owns the loop, watchers, timers, and allocator state. Server, client, thread pool, SSE, WebSocket, UDP, and the DNS resolver all sit on that same loop.

Two I/O models, one API

Readiness (epoll/kqueue/WSAPoll/poll) and completion (io_uring/IOCP) expose the same small contract to higher layers; the same generic driver runs across every completion backend.

Suspend and resume

Async handlers can suspend a connection and resume it from a file descriptor watcher, timer, client callback, or worker completion.

Body readers

Request bodies are routed into explicit readers: buffer, multipart, stream-oriented custom parsers, or application-specific sinks.

Streaming edges

Chunked responses, SSE, WebSocket frames, backpressure drain buffers, and client pools keep long-lived connections cheap.

Security model

A narrow surface, built to be constrained.

Keel keeps the byte-moving path small enough to test, fuzz, bound, and place behind kernel sandboxing. The init/run split and explicit resource limits make lockdown natural.

Resource limits at the edge

Header size, body size, multipart part limits, drain buffers, connection timeouts, idle timers, and route-level readers make overload behavior explicit. Chunked requests cap extension lists at 4096 bytes and trailer sections at 8192 bytes, rejecting bare LF and disallowed control bytes. HTTP/2 clients default to a 16 MiB body cap per stream.

Fuzzed protocol surfaces

Seven libFuzzer targets cover the untrusted-input attack surface: the HTTP parser, response parser, multipart, WebSocket, DNS responses, PROXY protocol, and URL parsing, all under ASan/UBSan; an optional gzip/deflate decompression target builds on demand. See docs/operations/fuzzing.md.

Bring your own hardening

TLS, allocators, DNS, compression, file IO, and parsers are vtables, so teams can choose the backend appropriate for their threat model.

Trust

Built like infrastructure.

Keel is intentionally boring in the places that matter: C11, static library, a wide CI matrix, sanitizers, fuzzing, static analysis, and examples that compile against the public API.
