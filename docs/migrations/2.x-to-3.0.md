# Migrating from Keel 2.x to 3.0

This guide is an actionable, source-level migration from the last 2.x release (tag v2.9.0) to Keel 3.0.
It is built from verified public-header diffs (old names checked against the v2.9.0 tree, replacements
checked against current main), not from commit chronology.

3.0 is a major version: it renames most of the public surface and removes a few installed headers.
Almost every migration is mechanical (rename an include, rename a type or function). This guide lists
every category, with before/after code.

## Compatibility promise (what 3.x guarantees)

- Keel is a C11 library. Its public C API has C linkage and is usable from C++11 consumers. There is
  no separate C++ wrapper API.
- Within the 3.x major version: SOURCE compatibility plus RECOMPILE / static-relink. Code that compiles
  against 3.y.z compiles against any later 3.y'.z' without edits; you rebuild your objects and re-link
  libkeel.a.
- NOT promised: cross-version binary ABI, stable struct sizes, a versioned shared object / soname, or
  stable opt-in `*_detail.h` layouts.
- The move from 2.x to 3.0 itself is a major bump precisely because it is not source-compatible; this
  guide is the one-time set of edits to make.

## 1. Header renames (update your #include paths)

The HTTP family gained `http_` / `http1_` / `http2_` prefixes so the installed surface names its
protocol. Update each include:

| 2.9.0 header | 3.0 header |
|--------------|------------|
| `keel/server.h` | `keel/http_server.h` |
| `keel/client.h` | `keel/http_client.h` |
| `keel/connection.h` | `keel/http_connection.h` |
| `keel/router.h` | `keel/http_router.h` |
| `keel/request.h` | `keel/http_request.h` |
| `keel/response.h` | `keel/http_response.h` |
| `keel/cors.h` | `keel/http_cors.h` |
| `keel/sse.h` | `keel/http_sse.h` |
| `keel/redirect.h` | `keel/http_redirect.h` |
| `keel/client_pool.h` | `keel/http_client_pool.h` |
| `keel/body_reader.h` | `keel/http_body_reader.h` |
| `keel/body_reader_multipart.h` | `keel/http_body_reader_multipart.h` |
| `keel/chunked.h` | `keel/http1_chunked.h` |

The umbrella `keel/keel.h` still exists and still includes the full public surface, so consumers that
include only `keel/keel.h` need no include edits (only the type/function renames in section 2).

## 2. Type and function renames

The rename is systematic: an HTTP type or function `Kl<Thing>` / `kl_<thing>_...` became
`KlHttp<Thing>` / `kl_http_<thing>_...` (HTTP/1-specific parsing is `KlHttp1*`, HTTP/2 is `KlHttp2*`).
The check-no-httplegacy gate guarantees no 2.x name survives anywhere in the tree, so if a name does
not compile, its replacement follows the pattern below.

Representative types (all verified old-in-v2.9.0 / new-on-main):

| 2.9.0 type | 3.0 type |

| `KlServer` | `KlHttpServer` |

| `KlClient` | `KlHttpClient` |
| `KlClientConfig` | `KlHttpClientConfig` |
| `KlClientResponse` | `KlHttpClientResponse` |

## 3. Removed integration headers (backends moved out of the installed surface)

Backend-specific headers are no longer installed under `keel/`. The core keeps the backend-neutral
vtable; the concrete adapter lives under `integrations/` and you point at it explicitly.

| 2.9.0 installed header | 3.0 core vtable header | 3.0 adapter (not installed) |
|------------------------|------------------------|------------------------------|
| `keel/tls_mbedtls.h` | `keel/tls.h` (`KlTls` vtable) | `integrations/tls/mbedtls/` |
| `keel/compress_miniz.h` | `keel/http_compress.h` (`KlCompress` vtable) | `integrations/codec/miniz/compress_miniz.h` |
| `keel/decompress_miniz.h` | `keel/decompress.h` (`KlDecompress` vtable) | `integrations/codec/miniz/decompress_miniz.h` |

Setup: include the core vtable header from `keel/`, and either add the integration source/header to
your build from its `integrations/...` path, or supply your own implementation of the vtable. The
adapter tracks the core vtable and recompiles against it; nothing is dynamically loaded.

## 4. KlEventLoop.fd removed

In 2.9.0, `KlEventLoop` exposed `int fd;` (the epoll/kqueue descriptor) and event functions took an
`int fd`. In 3.0 the descriptor is owned by the backend and is not on the public struct; the event ops
take a pointer-width `KlSocketHandle` (`keel/handle.h`).

- Do not read a loop descriptor. There is no supported "give me the event loop's fd" accessor; the
  backend owns it. If you were selecting on it yourself, drive the loop through the Keel event context
  (`KlEventCtx`, `kl_event_ctx_run`) instead.
- Native handles are `KlSocketHandle` (with `KL_INVALID_SOCKET` and `kl_handle_valid()`), not `int`, so
  a socket can be represented on platforms where a descriptor is not an int (Windows).

## 5. Types made opaque (use accessors, not fields)

These types are now forward-declared on the public surface; their layout moved to a private `src/`
header or an opt-in `*_detail.h`. Reaching into their fields no longer compiles. Use the accessors.

| Opaque type (3.0) | Was field access in 2.x | Use in 3.0 |
|-------------------|-------------------------|------------|
| `KlHttpConn` | `conn->response` | `kl_http_conn_response(conn)` / `kl_http_conn_response_const(conn)` |
| `KlHttpConn` | `conn->peer_addr` (string) | `kl_http_conn_peer_addr(conn)` |
| `KlWatcher` | struct fields | managed through `kl_watcher_add` / `kl_watcher_mod` / `kl_watcher_del` / `kl_watcher_rearm` |
| `KlTimerEntry` | struct fields | managed through the timer API (`keel/timer.h`) |
| `KlHttpClientPoolEntry` | struct fields | managed through the pool API (`keel/http_client_pool.h`) |
| `KlHttpMiddlewareEntry` | struct fields | registered through `kl_http_server_use` / `kl_http_router_use` |
| `KlWsServerConn` | struct fields | the WebSocket server send/close API (`keel/websocket_server.h`) |

## 6. Direct-field migrations (event loop, server port/context, connection response)

Even for structs that stayed concrete, F2 added accessors that are the supported way to read
library-owned state:

| 2.x direct field | 3.0 accessor |
|------------------|--------------|
| the event loop descriptor (`loop->fd`) | removed (section 4); drive via `KlEventCtx` |
| `server->bound_port` | `kl_http_server_bound_port(&server)` (still readable, but the accessor is the contract) |
| `&server->ev` (event context) | `kl_http_server_event_ctx(&server)` |
| `conn->response` | `kl_http_conn_response(conn)` |
| request-to-connection | `kl_http_request_conn(req)` |

## 7. Transport, datagram, and provider changes

These are additive relative to 2.9.0 (2.9.0 shipped no datagram or raw-transport public surface), so
they are not a break, but they are the new lower layer some code will want:

- New Tier-1 transports: `keel/stream.h` (`KlStream`), `keel/datagram.h` (`KlDatagram`),
  `keel/listener.h` (`KlListener`). Layouts are opt-in and unstable via `*_detail.h`.
- New socket/provider surface: `keel/socket.h` (`KlSocketProvider`), `keel/sockaddr.h` (`KlSockAddr`,
  address-ABI-neutral), `keel/handle.h` (`KlSocketHandle`), `keel/net.h`.
- Provider selection is build-time (`BACKEND=`) plus a caller-passed provider on `KlEventCtx.sockets`
  / `KlHttpServerConfig.sockets` / `KlHttpClientConfig.sockets`.
- There is no public `KlUdp` object API. If you used a pre-release `kl_udp_*` object type, move to
  `KlDatagram` (`keel/datagram.h`); the check-no-kludp gate keeps the old object API from returning.

## 8. Allocator and vtable validation now fail closed

3.0 validates caller-supplied allocators, providers, and vtables at their public boundary and returns
an error instead of accepting a malformed one (which in 2.x could be accepted silently or crash later).
If you passed a partially-filled vtable or an incomplete allocator, you now get a clean rejection:

- A malformed allocator at any public allocator boundary is rejected.
- A malformed vtable/provider is rejected where it becomes active: the HTTP/1 request-parser vtable at
  server init; the HTTP body-reader, HTTP/2 client and server session, TLS, compress/decompress
  vtables at their factory/init; the runtime event provider at install; the socket provider where it
  becomes active; the datagram provider on its path-specific requirements; a caller-supplied resolver
  at acceptance.

Migration: ensure required vtable ops are non-NULL and your `KlAllocator` is fully populated before you
pass it. The failure surfaces as a `-1` return with `KL_ERR_INVALID_ARG` (see `keel/error.h`) at the
init/factory/install call, rather than a later crash. Optional appended ops may be left NULL (they are
treated as "not supplied"), per the append-only, zero-default contract.

## 9. C++ linkage support and its limits

- Every installed `keel/*.h` compiles standalone under C11 and C++11 and guards its declarations with
  `extern "C"`, so C++ consumers can include and link the C API directly. This is gated in CI.
- Limit: there is no C++ wrapper API, no name-mangled C++ ABI, and no C++-only types. C++ is a
  consumption guarantee for the C API, nothing more.
- Limit: opt-in `*_detail.h` layouts are not ABI-stable in either language.

## 10. Install and pkg-config changes

- Installed headers are exactly the reviewed public set (a manifest, not a wildcard); backend-specific
  headers (section 3) and internal headers are not installed.
- The pkg-config module name is unchanged (`keel`); `pkg-config --cflags --libs keel` still works.
- The pkg-config `Version` now comes from the single-source root `VERSION` file, so it always matches
  the compiled `kl_version()` and `keel/version.h`.
- No shared object or soname is shipped; link `libkeel.a` statically as before.

## 11. Before / after

Minimal server:

```c
/* 2.9.0 */
#include <keel/server.h>
#include <keel/response.h>
static void hello(KlRequest *req, KlResponse *res, void *ctx) {
    (void)req; (void)ctx;
    kl_response_json(res, 200, "{\"msg\":\"hi\"}", 12);
}
int main(void) {
    KlServer s;
    KlConfig cfg = { .port = 8080 };
    if (kl_server_init(&s, &cfg) < 0) return 1;
    kl_server_route(&s, "GET", "/", hello, NULL, NULL);
    kl_server_run(&s);
    kl_server_free(&s);
}
```

```c
/* 3.0 */
#include <keel/http_server.h>
#include <keel/http_response.h>
static void hello(KlHttpRequest *req, KlHttpResponse *res, void *ctx) {
    (void)req; (void)ctx;
    kl_http_response_json(res, 200, "{\"msg\":\"hi\"}", 12);
}
int main(void) {
    KlHttpServer s;
    KlHttpServerConfig cfg = { .port = 8080 };
    if (kl_http_server_init(&s, &cfg) < 0) return 1;
    kl_http_server_route(&s, "GET", "/", hello, NULL, NULL);
    kl_http_server_run(&s);
    kl_http_server_free(&s);
}
```

Synchronous client:

```c
/* 2.9.0 */
#include <keel/client.h>
KlClientConfig cfg = { .timeout_ms = 5000 };
KlClientResponse resp;
/* args: alloc, cfg, method, url, headers, num_headers, body, body_len, resp */
if (kl_client_request(&alloc, &cfg, "GET", "http://example.com/", NULL, 0, NULL, 0, &resp) == 0) {
    /* ... use resp ... */
    kl_client_response_free(&resp);
}
```

```c
/* 3.0 */
#include <keel/http_client.h>
KlHttpClientConfig cfg = { .timeout_ms = 5000 };
KlHttpClientResponse resp;
/* args: alloc, cfg, method, url, headers, num_headers, body, body_len, resp */
if (kl_http_client_request(&alloc, &cfg, "GET", "http://example.com/", NULL, 0, NULL, 0, &resp) == 0) {
    /* ... use resp ... */
    kl_http_client_response_free(&resp);
}
```

Reading the response off an opaque connection (for example inside a thread-pool done callback):

```c
/* 2.9.0: direct field */
kl_response_json(&conn->response, 200, body, len);
```

```c
/* 3.0: accessor */
kl_http_response_json(kl_http_conn_response(conn), 200, body, len);
```

## 12. Compile-error troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `fatal error: keel/server.h: No such file or directory` (and the other renamed headers) | Header renamed | Update the include per section 1 (`keel/http_server.h`, ...) |
| `unknown type name 'KlServer'` (or `KlClient`, `KlConn`, `KlResponse`, ...) | Type renamed | Rename per section 2 (`KlHttp*` / `KlHttp1*` / `KlHttp2*`) |
| `implicit declaration of function 'kl_server_init'` (or `kl_client_request`, ...) | Function renamed | Rename per section 2 (`kl_http_*`) |
| `error: 'KlHttpConn' has no member named 'response'` / incomplete type | Type is opaque now | Use the accessor (section 5/6): `kl_http_conn_response(conn)` |
| `error: 'KlEventLoop' has no member named 'fd'` | `KlEventLoop.fd` removed | Do not read a loop fd; drive via `KlEventCtx` (section 4) |
| `fatal error: keel/tls_mbedtls.h` / `keel/compress_miniz.h` / `keel/decompress_miniz.h` | Backend header no longer installed | Include the core vtable header and add the adapter from `integrations/...` (section 3) |
| `kl_http_server_init` returns `-1` with `KL_ERR_INVALID_ARG` at startup | A vtable/provider/allocator you passed is malformed | Populate the required ops / allocator fields; optional appended ops may stay NULL (section 8) |
| C++ build: `error: ... does not name a type` on a `keel/*.h` include | (should not happen) all headers are C++11-clean | File a bug; the C++11 standalone compile is CI-gated (section 9) |
